## 4. 技术修正的具体内容

### 4.1 RSC 状态方向：复盘中最重要的发现

旧实现（可由 `git show de4b02a:src/ccsds_turbo.c` 复现）把寄存器方向解释为 `s0` 到 `s3` 的另一种排列，并使用：

```text
f = u XOR s0 XOR s3
p = f XOR s0 XOR s1 XOR s3
```

在当前采用的 `s0=最新寄存器位、s3=最旧寄存器位` 表示下，规范/独立向量对应的是：

```text
f = u XOR s2 XOR s3
p = f XOR s0 XOR s2 XOR s3
s3 = s2; s2 = s1; s1 = s0; s0 = f
```

代码位置：[`src/ccsds_turbo.c`](../src/ccsds_turbo.c) 中的 `ccsds_component_rsc_encoder` 和 `ccsds_init_trellis`。编码器和格形表必须使用同一方向；只改编码器而不改译码器会破坏内部闭环。

### 4.2 尾部终止和码字长度

旧实现把数据部分和两个分量的尾部拆开发送，R=1/2 还额外发送两个分量共 16 个尾部位；这会使实际发送长度偏离严格的 `2(K+4)`。

修正版让两个分量编码器都运行 `K+4` 个时刻，最后四个 switch bits 使状态回到零，并按整个时序统一复用：

```text
R=1/3: n = 3(K+4)
R=1/2: n = 2(K+4)
```

例如 K=1784 时，R=1/3 为 5364 bit，R=1/2 为 3576 bit；K=8920 时分别为 26772 bit 和 17848 bit。

### 4.3 R=1/2 复用/打孔

修正版在所有 `K+4` 个时刻使用同一相位：

```text
R=1/3: (sys, parity_a, parity_b)
R=1/2: 偶数 t 发送 (sys, parity_a)，奇数 t 发送 (sys, parity_b)
```

因此尾部也遵循相同的交替相位，不再有“数据区打孔、尾部另发一整块”的特殊分支。实现位于 `ccsds_multiplex_codeword`。

### 4.4 译码器观测映射

译码器先按实际发送序列读回 `K+4` 个时刻的 system/parity 观测；未发送的分量初始化为擦除（LLR=0），再分别交织/解交织并进入两路 Log-MAP。这样 decoder 看到的时序和 encoder 发送的时序相同，尾部不再依赖手工拼接的独立数组。

### 4.5 有效码率和噪声归一化

仿真使用有限块长的真实码率 `R_eff=K/n` 计算 `N0`，并在 CSV 元数据中同时写出 nominal rate、effective rate、block size 和 codeword size。这样不会把 4 个尾部时刻对高信噪比结果的影响悄悄忽略掉。

### 4.6 这几项应如何计数

如果按根因归类，本次有四项技术修正：

1. 尾部/状态归零；
2. R=1/2 码率匹配和码字长度；
3. 译码器观测映射与有效码率噪声计算；
4. RSC 状态方向及其与外部向量的一致性。

如果按项目里程碑归类，则可以写成三层：1 月已有实现和局部修复；8 月 29 日前的规范结构整理；8 月 29 日晚的 AFF3CT 状态方向修正。不要把每一个 Git commit 或每一次补测都称作一次独立技术修正。

## 5. 为什么 1 月的测试会通过，问题为什么没有一开始发现

这部分是复盘报告中最值得写清楚的工程经验。

### 5.1 内部自洽会掩盖外部不一致

旧编码器和旧译码器使用相同的寄存器方向、相同的尾部拆分方式。无噪声时，编码器产生的码字被同一套假设译回原消息，所以闭环为零错误。这个结果不是假的，但它只回答了一个较弱的问题：“这套程序内部是否自洽？”

### 5.2 性能曲线仍可能看起来合理

Turbo 码的瀑布区受码率、块长、迭代次数和信道模型共同影响。即使码字顺序有偏差，只要 encoder/decoder 彼此配套，曲线仍可能有正确的单调下降趋势和大致门限位置。因此仅凭“图线像 Green Book”不能反推出码字排列已经符合规范。

### 5.3 当时的时间重点在性能产出

1 月临近 PPT 截止，优先事项是完成四种配置、生成 BER/FER 图和解释卷积码/Turbo 码差异。没有现成的外部逐字节向量，也没有把标准复用图翻译成自动化断言；这是一个常见的验证覆盖缺口。

### 5.4 复盘后的定位路径

后续按“规范文字 → 独立固定向量 → 外部实现 → 大规模性能”的顺序检查：

1. 从 Blue Book 第 6 节核对 `G0/G1`、尾部和码字排列；
2. 用 12 bit 小向量手算并固定系统位、校验位和尾部；
3. 用 8 时刻向量检查 R=1/2 打孔相位；
4. 用 K=1784/3568/7136/8920 检查长度和无噪声闭环；
5. 与公开的 AFF3CT/ocaml-turbo 向量比较，发现 `f` 应使用 `s2 XOR s3`；
6. 修改 encoder、trellis、decoder 观测映射后重新运行上述测试。

这条路径说明为什么问题在复盘阶段才被定位，也说明为什么不能用“当时跑了两个晚上”替代码字级证据。

之后的 `output/24`、`27`、`28`、`30`、`31`、`32`、`33` 是定点续跑、补测或跨主机拆分；`output/22` 是后处理，`output/23` 是确定性/外部向量验证，两者不另计为大规模仿真迭代。

如果把每个主机、每个 SNR 队列都单独计数，campaign 数量会超过 8。报告中应同时说明“8 个主线阶段 + 若干续跑/补测”，这样既不把并行任务重复计数，也不掩盖实际投入。

### 7.2 分片调度和终止条件

[`ccsds_parallel_runner.py`](../scripts/ccsds_parallel_runner.py) 的基本原则是：

- 一个 worker 只负责一个固定 SNR 的分片；
- 分片完成后才进入聚合；不读取半写入 CSV；
- 聚合保存的是 `Bit_Errors`、`Total_Bits`、`Frame_Errors`、`Total_Frames` 的整数和，而不是各分片 FER 的简单平均；
- 通过临时文件和原子替换更新 aggregate，停止后可以继续；
- 每个分片保留在 `shards/`，以便重新审计。

不同阶段使用过两套早停口径，不能混写：

| 阶段/脚本 | SNR 点完成条件 | 上限 |
|---|---|---|
| `run_ccsds_1784_trimmed_completion.sh`、早期 8920 任务 | 至少 1000 帧后累计 100 个错误帧，或达到目标帧数 | 每点 3,000,000 帧 |
| 后续 clean/续跑脚本 | 至少 1000 帧后累计 300 个错误帧，或达到目标帧数 | 每点 3,000,000 帧 |
| `cloud_convergence_stop.py`（可选监视器） | 至少 1,000,000 帧；科学计数法两位表示在 200,000 帧内稳定；与参考的绝对 `log10` 误差不超过 0.30 | 由 runner 的时间/帧上限约束 |

达到“错误帧数”只说明点估计有足够的事件，达到 3M 帧只说明到达硬上限；两者都不等于与参考曲线完全重合。低 FER 点仍需看置信区间和误帧数。

### 7.3 统计和图线改进

相对于 PPT 版，本次新增或统一了：

- FER 的 95% Wilson 区间；
- `log10(measured FER / reference FER)`，避免在极小 FER 区域只看百分比造成误判；
- 参考曲线只画到实际测量的 SNR 范围，避免“参考多一个点”；
- 黑白打印友好的线型和 marker，实测/参考成对出现在左下角图例；
- 每个数据点保留来源主机、目录、分片数量和坏分片数量。

## 9. 当前性能结果和 Green Book 的关系

### 9.1 参考曲线的数字来源

Green Book 图 7-6/7-9 给出曲线和坐标口径；脚本中的逐点数字来自已核对的 NASA DSN 810-005 Module 207 Tables A-3/A-4。比较指标是：

```text
log10_fer_ratio = log10(measured_FER / reference_FER)
```

`0` 表示点估计相等，`+0.30` 约为参考的 2 倍，`-0.30` 约为参考的一半。对数误差比原始百分比更适合跨越多个数量级的 FER 曲线。

### 9.2 严格 post-AFF3CT 点的判断

- **K=1784、R=1/2：** clean 点从 0.6 到 1.8 dB 已覆盖，低到中 FER 区域总体接近参考；1.6 dB 的误帧较少，统计区间仍比点估计更值得关注。
- **K=1784、R=1/3：** -0.4 到 0.8 dB 均有 clean 分片，曲线下降位置和 Green 参考基本一致；0.8 dB 已进入低 FER，误帧数仍需在图注中说明。
- **K=8920、R=1/2：** 0.5–1.0 dB 的 clean 迷你主机数据整体接近；1.1 dB 只有 3 个误帧，1.2 dB 为 0 个误帧，不能据此断言高 SNR 已与参考重合。1.3 dB 目前没有严格 clean 点。
- **K=8920、R=1/3：** 停机备份的 0.0–0.5 dB 可用于一张明确标注来源的 post-fix 停止快照；`output/29` 因远端连接关闭没有把它们自动纳入实时状态表，二者不是矛盾，而是“实时审计”和“停机备份”两个时间点。

### 9.3 `output/36` 数值摘要（仅作为混合来源叠加）

| 配置 | 点数 | 平均绝对百分比误差 | 解释 |
|---|---:|---:|---|
| K=1784，R=1/2 | 7 | 25.11% | 含 `output/18` 修正前数据；不能用来证明当前代码性能 |
| K=1784，R=1/3 | 7 | 7.72% | 同上 |
| K=8920，R=1/2 | 9 | 225.24% | 高 SNR 点偏离明显，且混有旧 aggregate/少量增量；应优先作为待核查信号 |
| K=8920，R=1/3 | 6 | 18.24% | 三个停机备份目录均按完整分片聚合，来源最干净，但低 SNR 点帧数不均衡 |

这里的百分比是脚本历史输出中的 `abs(FER/reference-1)` 平均值；正式报告应同时给出误帧数、帧数和 `log10` 误差，不能只报一个平均百分比。特别是 K=8920 R=1/2 的 1.1–1.3 dB，样本量和版本混合都足以放大百分比。
